# Jazz Setlist

Setlist manager for a jazz drummer: per-user tune arrangements, show setlists with set breaks, and a metronome per tune.

## Stack

- JavaScript only (no TypeScript). ES modules everywhere.
- Frontend: Svelte 5 (runes) SPA, hash routing (`src/client/lib/router.js`), plain CSS with tokens in `src/client/app.css`.
- Backend: Hono on Cloudflare Workers. Hono JSX (`.jsx`, `jsxImportSource: hono/jsx`) for server-rendered HTML; the page shell is `src/server/shell.jsx`.
- DB: Cloudflare D1 + Drizzle ORM (`src/db/schema.js`), migrations in `drizzle/` generated by drizzle-kit.
- Validation: Zod (`src/shared/validation.js`), shared by server and any client code.
- Build/dev: Vite 8 + `@cloudflare/vite-plugin` (runs the Worker inside `vite dev`) + `@sveltejs/vite-plugin-svelte` + `vite-plugin-pwa`.
- Tests: Vitest (node project + browser project: Svelte components in Chromium via `@vitest/browser-playwright` and `vitest-browser-svelte`). Lint: ESLint 10 flat config (`eslint.config.js`) with `eslint-plugin-svelte`.

## Layout

```
src/
  server/      index.jsx (Hono app + shell route), shell.jsx, middleware/auth.js, routes/*.js, lib/http.js
  db/          schema.js (all tables), index.js (createDb)
  shared/      attributes.js (enums, labels), validation.js (Zod), setlist.js (numberSets, moveItem), preferences.js
  client/      main.js, App.svelte, app.css, pages/, components/, lib/ (api, router, metronome, session)
drizzle/       SQL migrations (generated; do not hand-edit). Data migrations: `drizzle-kit generate --custom --name=<name>`
```

## Commands

```bash
pnpm dev                # Vite + Worker on http://localhost:5188
pnpm test               # Vitest: node tests + component tests in Chromium (needs `pnpm exec playwright install chromium` once)
pnpm test:e2e           # Playwright end-to-end tests (e2e/), own dev server on :5189 with a fresh local D1
pnpm lint               # ESLint
pnpm check              # lint + test + build — run before calling work done
pnpm db:generate        # drizzle-kit generate after editing src/db/schema.js
pnpm db:migrate:local   # apply migrations to local D1 (.wrangler/state)
pnpm db:migrate:remote  # apply to production D1
pnpm release            # build, apply remote migrations, wrangler deploy (manual deploy)
pnpm icons              # re-render favicon + PWA PNGs from public/favicon.svg (ImageMagick)
pnpm import:polynome <backup.pln> <email> [--local|--remote]   # PolyNome backup -> tunes + setlists
```

`pnpm deploy` is pnpm's built-in workspace command, not a script; never name a script `deploy`.

## Deployment (GitHub Actions → Cloudflare)

- Repo: `git@github.com:cyface/jazz-setlist.git`, branch `main`. Everything (Worker + D1 `jazz-setlist`) lives in the timlwhite Cloudflare account `16805f1fb394761354e4f3f30bafa8c4`, set by `account_id` in `wrangler.jsonc`. Never deploy to another account.
- `.github/workflows/ci.yml`: every PR runs `pnpm check` and, in a second job, `pnpm test:e2e` (report and traces uploaded as an artifact on failure).
- `.github/workflows/deploy.yml`: every push/merge to `main` runs `pnpm check`, then `pnpm release:ci` (applies pending D1 migrations, then `wrangler deploy`). Needs repo secret `CLOUDFLARE_API_TOKEN` (timlwhite account: Workers Scripts Edit + D1 Edit).
- Work on a branch and merge by PR (`gh pr merge --squash`); head branches are deleted on merge. Merging to `main` deploys to production.
- `pnpm build` writes `dist/client` (assets) and `dist/jazz_setlist/wrangler.json`; `wrangler deploy` picks up that generated config automatically.
- Local D1 state under `.wrangler/state` is keyed by `database_id`; if the ID changes, rerun `pnpm db:migrate:local`.

## Auth (Cloudflare Access / Zero Trust, same pattern as cyface-invoice)

- Cloudflare Access protects the whole custom domain. The Worker reads `CF-Access-Authenticated-User-Email` and auto-provisions a `users` row (`src/server/middleware/auth.js`).
- Local dev: `.env` (copy from `.env.example`) sets `DEV_AUTH_EMAIL`; it is honored only for `localhost`/`127.0.0.1`. Do not create a `.dev.vars`: when it exists, wrangler ignores `.env`.
- `workers_dev` and `preview_urls` are `false` so the Worker is reachable only through Access. Never enable them: the header is trusted, so a public URL would let anyone impersonate a user.
- Every query on `arrangements` / `setlists` filters by `user_id`. Setlist item writes verify each `arrangementId` belongs to the user.

## Data model

- `arrangements`: title, composer, musical_key, tempo (bpm), beats_per_bar + beat_unit (time signature, e.g. 6 + 8 = 6/8; `timeSignature()` in attributes.js), `feel` (swing|straight|bossa|latin), `drum_implement` (sticks|brushes), `drums_entry` (top|later) + `drums_entry_note`, `solo_order` (JSON), notes.
- `solo_order` entries: `{type:'solo', instrument}`, `{type:'trade', instruments:[≥2], bars:2|4|8}`, `{type:'over_head', instrument}` (e.g. drums solo over the head out). Instruments are free text, lowercased; suggestions in `INSTRUMENTS`. Solo-order chips show the instrument's icon (`soloEntryIcons()` / `instrumentIcon()` in attributes.js, which also maps common aliases like tenor → sax); unknown instruments fall back to the mic. A new entry in `INSTRUMENTS` needs an icon branch in `Icon.svelte`.
- `users.preferences` (JSON, null = defaults): `{ hideDefaults, sound, defaults: { feel, drumImplement, drumsEntry, timeSignature } }` (timeSignature is a string like "4/4" from `TIME_SIGNATURES`). `resolvePreferences()` (`src/shared/preferences.js`) merges stored values over `DEFAULT_PREFERENCES`; the auth middleware attaches the result to the user. Defaults prefill new tunes; with `hideDefaults`, compact `TuneBadges` (list views) leave out attribute values equal to the default.
- `setlists` + `setlist_items` (`kind` tune|break, `position`). `setlists.archived_at` (null = active) archives a setlist without deleting it; the list page has Active / Archived tabs (`#/setlists`, `#/setlists/archived`). `PUT /api/setlists/:id/items` replaces all items in one D1 batch. Deleting an arrangement cascades out of setlists.
- Adding an attribute value: extend the enum in `src/shared/attributes.js` (+ `LABELS`), add an icon branch in `Icon.svelte`, a badge color token in `app.css`, and the option in `src/client/lib/choices.js`. Enum columns are TEXT, so no migration is needed for new values.

## API

`/api/me` (user + preferences), `PUT /api/me/preferences`, `/api/arrangements[/:id]` (GET/POST/PUT/DELETE), `/api/setlists[/:id]` (GET/POST/PUT/DELETE), `PUT /api/setlists/:id/items` (replace all), `POST /api/setlists/:id/items` (`{ arrangementId }`, appends one tune), `PUT /api/setlists/:id/archived` (`{ archived: boolean }`). Errors are `{ error }` or `{ error, issues: [{path, message}] }` on 400.

## Frontend conventions

- Layout mirrors cyface-invoice's AppShell: `Sidebar.svelte` is a drawer opened by the top bar's hamburger below 768px, an icon rail from 768px and a full sidebar from 1024px; its nav is Tunes / Setlists / Preferences, with the app version (`__APP_VERSION__`) at the bottom. `Topbar.svelte` has the theme toggle and the user avatar menu (email, Preferences, Log out via `/cdn-cgi/access/logout`).
- `lib/session.svelte.js` holds the signed-in user and preferences (`$state`); `App.svelte` loads it before rendering any page, so pages can read `session.preferences` synchronously.

- Tunes list: active (unarchived) setlists show at the top as links (`ActiveSetlists.svelte`; nothing when there are none), so the current show is one tap away. Shared setlist helpers (active filter, date · venue, tune count) are in `lib/setlists.js`.
- Tunes list: holding a row on a touch screen (or right-clicking it with a mouse) opens an action menu (`lib/longpress.js` action, `AddToSetlist.svelte`) with "Add to <setlist>" for each active setlist (`addMenu()` in `lib/add-to-setlist.js`, using `GET /api/setlists?contains=<id>` → `hasTune`); nothing is added until one is picked. If the only active setlist already has the tune, the menu says so instead of offering it. With no tune selected, list pages use the full width; the detail column appears only for a selection.
- Setlist page: Next shows the next tune's name (and its set when it starts a new one). The last tune opened stays highlighted and scrolled into view after going back to the list; `lib/setlist-position.js` keeps it per setlist in localStorage as index + arrangement id, since item ids change on every save. Tunes are added with `TuneSearch.svelte` (combobox; ranking in `searchTunes()`, `lib/search.js`, ignores case, accents and punctuation). A tune's Edit button carries the setlist and tune index (`editTuneHref()` in `lib/router.js`), so the tune form's Save and Cancel come back to that tune open in the setlist (`afterEditPath()`: `#/setlists/<id>?tune=<index>&arrangement=<id>`, which the page opens once by index + arrangement id and then drops from the URL; a setlist or tune gone since shows the tune instead, `tunePageInstead()`; leaving the form replaces its history entry, so Back skips it). Edit is a mode (`editing`, left with Done): only then do rows show move up/down/remove and break notes become inputs (outside it they're plain text, and `move()`/`remove()` return early); the add-tune bar is always shown. In edit mode, Details opens the name/date/venue/notes form (`editingInfo`), which also holds Archive/Restore and Delete, away from the toolbar.
- Last page: `lib/last-route.js` remembers the current route in localStorage with the user's id (not forms), and `App.svelte` restores it after the session loads when the app opens without a hash (the PWA's start URL), so a reopened app goes back to the setlist; another user starts on Tunes.
- Offline: `lib/offline.js` keeps one localStorage copy (`offline-copy`) of `/api/me`'s user and every active setlist with full tune details; `lib/api.js` updates it from responses (archived/deleted setlists and deleted tunes leave it; edited tunes are patched in) and, on a network error (`OfflineError`; GETs also time out after `READ_TIMEOUT_MS`, writes never do), answers `me`, `listSetlists()` and `getSetlist()` from it. `saveActiveSetlistsOffline()` fetches every active setlist after the session loads, when the app returns to the foreground (at most once a minute) and when it comes back online. `connection.offline` (`lib/connection.svelte.js`, set by every request) shows the offline banner in `App.svelte` and hides edit controls; the setlist page shows "Saved copy from …" and reloads when back online, keeping the open tune (and its metronome) by index + arrangement id. A different user replaces the copy and clears tune positions; Log out clears the copy, the last route and positions. An expired Access session also looks like a network error, hence the banner's "reload to sign in" hint.
- Icons are hand-drawn inline SVG in `src/client/components/Icon.svelte`; every attribute shows as an icon (with label, or with tooltip/`aria-label` in compact mode) via `TuneBadges.svelte`.
- Metronome: `src/client/lib/metronome.js` is a Web Audio lookahead scheduler (clicks scheduled on the audio clock, beat squares lit by `requestAnimationFrame`). Keep timing logic in pure functions (`planBeats`, `isAccent`, `tapTempo`) and test them. Space bar toggles play; screen wake lock is held while playing. `preferences.sound` (default on) turns the clicks off while the beat lights keep flashing; the metronome's mute button overrides it until reload or the next preferences save (`session.soundOverride`, `soundOn()` in `lib/session.svelte.js`).
- Dark mode is required. Every color is a token on `:root` in `app.css` written as `light-dark(<light>, <dark>)`; never hardcode colors in components, and give every new token both values.
- Theme: `color-scheme: light dark` follows the OS; the top-bar toggle (System → Dark → Light) sets `data-theme` on `<html>` and stores it in localStorage (`src/client/lib/theme.js`). `THEME_BOOT_SCRIPT` (`src/shared/theme.js`) is inlined in the shell `<head>` so the saved theme applies before first paint. Check UI changes in both themes.
- Production asset names are fixed (`/assets/app.js`, `/assets/app.css`, cache-busted by `?v=<package version>`) because the Hono shell references them. Bump `package.json` version on each release.
- PWA (setup mirrors cyface-invoice): `vite-plugin-pwa` in `vite.config.js` (client environment only) builds `manifest.webmanifest`, `sw.js` and precaches `/assets/*` + favicons; `?v=` is ignored when matching the precache. There is no index.html, so the shell links the manifest (production only, `crossorigin="use-credentials"` for Access) and `main.js` registers `/sw.js`. Navigations are NetworkFirst (cached shell only offline) so an expired Access session still redirects to the login. `app.js` and `app.css` keep fixed names, so `dontCacheBustURLsMatching` limits revision-less precaching to hashed chunks; their revisions are what change `sw.js` each release. The worker skips waiting and claims clients (set in `workbox`: the plugin adds them only when it injects the registration, and `main.js` registers `/sw.js` itself), so a release takes over open pages and a first visit is offline-ready without a reload; `scripts/check-sw.js`, run by `check` and `release`, fails a build missing the revisions or either of these. The precached `app.js` (matched ignoring `?v=`) is what a page loads first, so `main.js` reloads once on `controllerchange` when a new release's worker takes over (held while the metronome plays: `lib/reload-guard.js`), and calls `registration.update()` whenever the app becomes visible. Icons are rendered from `public/favicon.svg` (`pnpm icons`). `InstallPrompt.svelte` shows a phone-only install banner; its logic is in `lib/install.js`. Access bypass rules for the static PWA paths are listed in `wrangler.jsonc`.

## PolyNome import (`scripts/polynome/`)

Imports a PolyNome Pro backup (`.pln`, git-ignored) as tunes and setlists. Pipeline: `extract.py` (decodes the NSKeyedArchiver plist via `unarchive.py`, maps preset names to canonical titles in `CANON`; the rest of a name is cue text) → `transform.py` (emoji cues → fields: 🥢 sticks, 🖌 brushes, 🎤 drum solo, 🐟 bass, 💹 trading, 🚫🥁 drums later, 🇧🇷 bossa, 💃 or "LATIN" (any case) latin, 📏 straight, checked in that order on the newest preset name (titles in `BOSSA` / `LATIN` / `STRAIGHT` get that feel without the cue; tested by `transform.test.js`, which runs `python3`); 6 or 12 beats → 6/8, 12/8; tempo from the newest standalone preset; per-tune solo orders in `SOLOS`; all setlists but the active one archived) → `to-sql.js` (validates with the app's Zod schemas, emits idempotent SQL keyed on the user's email). Output goes to `scripts/polynome/out/` (git-ignored). A new tune name in a backup needs adding to `CANON` (extract prints `UNMAPPED` setlist items). Run Python with `-I`.

## Testing

- Server tests use a real in-memory D1 from Miniflare with all migrations applied (`src/server/test-env.js`); call the app with `app.request(url, init, env)`.
- New behavior gets a test in the same change; bug fixes get a regression test.
- Test files sit next to source as `*.test.js`.
- Component tests: `src/client/**/*.browser.test.js` run in a real Chromium (Vitest browser mode, `browser` project in `vitest.config.js`). `await render(Component, props)` from `vitest-browser-svelte`, query with locators (`screen.getByRole(...)`) and assert with `expect.element(...)` (it retries) or `expect.poll`. Mock `lib/api.js` with `vi.mock` so tests need no Worker or D1; test data shapes are in `src/client/test/fixtures.js`. `src/client/test/setup.js` resets the hash, localStorage and `connection.offline` before each test. Give `beforeEach` a block body: a function it returns (e.g. `() => mock.mockReset()` returns the mock) runs as cleanup after the test. Page logic (routing, offline, edit mode) belongs here; pure logic stays in node tests.
- End-to-end tests: `e2e/*.spec.js` (Playwright, Chromium), for flows across the Worker, D1 and client. `playwright.config.js` starts `vite` with `E2E=1` (see `vite.config.js`): port 5189, a fresh D1 under `.wrangler/e2e` with all migrations, and the fixed user `e2e@example.com` (`.env` isn't loaded; `vite build` refuses `E2E=1`, and `scripts/check-deploy-config.js`, run by `check` and `release`, fails a build whose generated `wrangler.json` sets any vars), so a running `pnpm dev` and your dev data are untouched. Tests run one at a time; the `data` fixture (`e2e/fixtures.js`) creates tunes/setlists through the API and deletes them afterwards, and `gig` is a ready-made two-set setlist. Phone tests use `devices['Pixel 7']`; `longPress()` sends real touch events over CDP. The `pwa` project (`e2e/pwa.spec.js`) tests the service worker against `vite preview` of a normal `pnpm build` on port 5190 (D1 under `.wrangler/e2e-preview`; the test user comes from `dist/jazz_setlist/.dev.vars`, which only local preview reads): precache, offline reload, and the reload when a new release takes over (the test fires `controllerchange`, since preview answers a changed `sw.js` with 304 and Playwright can't route the worker script fetch). Keep the suite small (main flows); details go in component tests.
